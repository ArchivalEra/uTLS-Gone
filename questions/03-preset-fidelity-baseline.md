# 03: 预设表的保真基准取哪一边

**What to build:** 一个明确的、可复跑的「预设表是否正确」的判据来源。

预设表（每个浏览器版本的一整套：密码套件顺序、扩展顺序与内容、GREASE 位置、填充、
密钥共享组）可以有三种来源，各有代价：

1. **从 Go uTLS 的 `u_parrots.go` 逐条移植** —— 与参照实现对齐，但那是别人的选择，
   且它本身也有版本滞后的记录（其预设的 Chrome 版本落后于下游生态）。
2. **从真实浏览器抓包反解** —— 最接近「真」，但一条抓包无法揭示「每连接是否乱序」
   这类行为（见 STATE.md 的已知缺口），得靠多条抓包统计。
3. **直接抄在线核对端点的输出** —— 省事，但那是二手数据，且端点本身会变。

这个选择决定了「保真」这个词在本仓的定义，所以它必须先被定下来 ——
否则每个预设的评审都会重新吵一遍，而每次吵的结论可能不同。

**Blocked by:** None (can start immediately)

**Status:** resolved

**Settling:** 不存在 —— 本工单的第一交付物是 `fixtures/` 语料目录的一份 README，
写明本仓认哪一边为基准、另外两边各自的用途（交叉验证 / 统计行为），
以及一条能把基准换成另一边时的迁移说明。

## 结论（结案）

**基准 = Go uTLS 自己的产出，而且刻意用两个互相独立的见证去接它**：
① 上游**录音**（`crates/utls/tests/fixtures/utls-testdata/`，39 条逐字节）；
② 上游 **API 产出**（`utls-reference.json`，39 个预设逐字段）。两者接法不同、覆盖面不同，
缺一不可（真缺陷里有的只有①抓得到、有的只有②抓得到）。

另两个来源**不是基准**：真实抓包用于「形状」的交叉验证与「行为」的统计；
在线端点（browserleaks）用于验证**发射路径**（服务器所见 == 我们发出的字节 == 台账黄金值）。
完整的取舍、四类差异的**实测对比**（真实抓包 vs Chrome-70/58 预设：版本滞后 / 扩展集合 /
GREASE 位置与取值 / 密码套件集合），以及**换基准要动什么**，写在
`crates/utls/tests/fixtures/README.md`。

工单里那条「抓一份真实 Chrome 的 ClientHello，与同预设产出逐字段比」已经做了 ——
语料用的是 uTLS 测试内联的那条真实抓包（`raw-capture.bin`），差异逐条记在上面那份 README 里。
结论是：抓包**能**指出上游预设在哪里落后（版本滞后为主），但**不能**给出「正确的那一份」，
因为它只是一次连接、一个版本 —— 这正是它只能当交叉验证的原因。

**Settling:** `crates/utls/tests/fixtures/README.md` —— 该文件存在且写明「认哪一边为基准」与另两边的用途 ⇒ 结论成立；被删或改成「三家并列」⇒ 结论要重议
